# Phase 1, checkpoint 2 — ERP schema

## Goal

Create the 12 empty ERP tables as `queryguard_owner`, then verify their real
PostgreSQL catalog metadata and access permissions. Seed data is deliberately deferred until the Safe Execution demo.

## Tables

| Table | Purpose |
| --- | --- |
| `customers` | Customer identity, geography, segment, and credit limit |
| `suppliers` | Product suppliers and purchasing terms |
| `product_categories` | Hierarchical product classification |
| `products` | Product, category, primary supplier, cost, and USD list price |
| `warehouses` | Physical inventory locations |
| `inventory` | Current product quantity by warehouse |
| `employees` | Staff, departments, managers, and warehouse assignment |
| `sales_orders` | Customer sales-order headers |
| `sales_order_items` | Products, quantities, prices, discounts, and fulfillment warehouse |
| `purchase_orders` | Supplier purchase-order headers |
| `purchase_order_items` | Ordered and received product quantities and costs |
| `product_returns` | Customer returns and refunds linked to original sales lines |

## Engineering decisions

- Surrogate keys use `GENERATED BY DEFAULT AS IDENTITY`. PostgreSQL generates
  IDs normally, while a later tiny deterministic fixture can still insert explicit IDs.
- Monetary values use `numeric`, not floating-point types.
- All prices and order amounts use USD so aggregate results are meaningful
  without an exchange-rate model.
- `line_total` is a stored generated column on both line-item tables, avoiding
  inconsistent application-side calculations.
- Every primary key, foreign key, unique constraint, and check constraint is
  named so failures are diagnosable.
- Foreign keys use `RESTRICT`; this synthetic ERP preserves transaction
  history instead of deleting dependent rows automatically.
- PostgreSQL already indexes primary keys and unique constraints. The 19
  explicit indexes cover remaining foreign-key lookups and common reporting
  filters.
- Table comments and key financial-column comments prepare the metadata needed
  by the schema inspector in Phase 2.
- Constraints involving multiple rows or tables, such as total returned
  quantity not exceeding sold quantity, cannot be expressed as ordinary
  `CHECK` constraints. A later tiny deterministic fixture will enforce those rules.

## Apply to the current database

Your PostgreSQL volume already exists, so Docker will not automatically run the
new initialization script. Run these commands from the repository root.

```bash
docker compose ps
```

Shows the project containers. Confirm that `postgres` is `healthy` before
continuing.

```bash
bash database/apply_schema.sh
```

Runs `database/schema.sql` inside the existing PostgreSQL container while
logged in as `queryguard_owner`. The SQL is transactional: an error rolls back
the entire schema operation.

Expected final output:

```text
COMMIT
```

The command is intentionally a one-time migration. If PostgreSQL reports that
a relation already exists, the schema was already applied; run the tests rather
than applying it again.

For a completely new empty Docker volume, `database/init/10_erp_schema.sh`
runs automatically after the role initialization script.

## Verify the schema

Load the local environment variables into the current Terminal session:

```bash
set -a
source .env
set +a
```

- `set -a` exports variables created by subsequent shell commands.
- `source .env` reads this project's local database settings and passwords.
- `set +a` turns automatic exporting back off.

Run only the new schema tests:

```bash
QUERYGUARD_RUN_DB_TESTS=1 pytest tests/integration/test_erp_schema.py -v
```

The temporary variable enables database-dependent tests; `pytest` runs the
schema test file, and `-v` displays every test name. Expected result:
`8 passed`.

Run both the role-security and schema suites:

```bash
QUERYGUARD_RUN_DB_TESTS=1 pytest tests/security tests/integration -v
```

This proves the role boundaries still hold after creating tables and that the
runtime role can read, but cannot modify, every ERP table. Expected result:
`24 passed`.

Run all ordinary development checks:

```bash
ruff check .
ruff format --check .
mypy
pytest
```

- `ruff check .` finds common Python errors and code-quality problems.
- `ruff format --check .` verifies formatting without changing files.
- `mypy` checks Python type annotations.
- `pytest` runs ordinary tests; database tests skip unless explicitly enabled.

Expected ordinary pytest result: `1 passed, 24 skipped`.

## What the tests prove

- Exactly 12 expected ERP tables exist.
- Every table is owned by `queryguard_owner` and has a description.
- Column counts and primary keys match the design.
- All 19 foreign-key relationships exist.
- All 59 check constraints are named and validated.
- All 19 additional indexes exist.
- `queryguard_runtime` has `SELECT`, but no table-write privilege.
- Real `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `ALTER`, and `DROP` attempts
  by `queryguard_runtime` are rejected, even after its read-only session default
  is deliberately disabled.
- `queryguard_audit` has no ERP table access.
- The runtime role can query all 12 currently empty tables.

## Common errors

- `service "postgres" is not running`: open Docker Desktop and run
  `docker compose up -d postgres`.
- `password authentication failed`: the passwords in `.env` differ from those
  stored when the Docker volume was first initialized.
- `relation ... already exists`: the one-time schema migration has already run;
  continue with the tests.
- `permission denied for schema erp`: the schema command was not executed as
  `queryguard_owner`; use `bash database/apply_schema.sh`.
- `pytest: command not found`: activate the project environment with
  `source .venv/bin/activate`.
